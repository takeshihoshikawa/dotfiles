# Morning

Read [the shared contract](secretary-contract.md) before acting. This file is the shared workflow for Claude Code, ChatGPT Work, and Codex. Follow the active global instructions when an older example conflicts with them.

1日の Introduction を作る。`daily-report` が同じ項目へ Results / Discussion を返せるよう、計画を当日の日報へ永続化する。

## 対象日

- 引数に `tomorrow` があれば明日、それ以外は今日。
- タイムゾーンは `Asia/Tokyo`。

## 朝夕の対応

| morning | daily-report |
|---|---|
| 文脈 | 目標への寄与 |
| プロジェクト優先順位 | 実際のプロジェクト配分と逸脱 |
| 今日の主題・問い | 得られた答え・残った問い |
| 期待する成果 | 実際の成果 |
| 本人／委任の分担 | 本人の活動／委任成果 |
| エフォート予算 | エフォート実績 |
| 制約・リスク | 計画差と理由 |
| 完了条件 | 達成証拠 |

## 週次との対応

`weekly-review`が作成した対象週の計画を、その日の既定方針として具体化する。

- `python3 ~/work/projects/admin/scripts/report_period.py --date {対象日}`の`current`を使い、土曜〜金曜の期間内の月曜をキーとする`weekly/weekly-{Monday}.md`の`## 週の計画`を読む。土日は次の月曜のノートになる。旧週報は既存の`period`を優先する。
- 現行形式がない場合だけ、直前週の`## 来週の計画`または`## 来週の重点`を移行用の参考情報として読む。
- 週次で決めたプロジェクトの役割、期待成果、本人と委任の分担、エフォート予算を、当日の利用可能時間へ落とし込む。
- 新しい締切、体調、依存関係、前日の結果などの根拠がなければ、週次の役割を朝だけで変更しない。
- 週次計画から外れる提案をする場合は、変更内容と理由を明示し、`daily-report`で追跡できる形にする。

### 文脈

- `notes/goals.md`
- 対象週の`weekly/weekly-{Monday}.md`にある`## 週の計画`

- 前日の日報では特に`## 気づき`と`## 次への引継ぎ`を読む。

## 計画を作る

収集結果から次を提案する。単なるタスク列挙ではなく「今日の終わりに何が変わっていれば成功か」を定義する。

### 作業の選択と配置

1. **午前の集中を優先する。** `goals.md`の仕事の過ごし方と本人の最新の指示を配置条件として使い、特に10:30ごろまでは本人が考える・作る作業を連続して置く。対象はその日の優先順位で選び、授業準備も含む。固定予定・期限などで事務を先に置く必要があれば、その理由を示す。「今日やる」という指定だけで朝一番とは解釈しない。
2. **空き時間から仕事を作らない。** 未解決の仕事と本人・委任の分担を確かめ、必要な時間を見積もってから配置する。空きを埋めるために作業を増やしたり、委任した仕事を本人へ戻したり、別の目的の作業へ置き換えたりしない。新しい根拠による変更は理由を示し、残った時間は余裕として残す。

### 文脈

- 長期目標との接続を1–2点に絞る。
- 当週の週次計画から引き継ぐ役割・期待成果・エフォート予算を要約する。
- 前日の結果・気づき・引継ぎを3–5項目で要約する。

### プロジェクト優先順位

個別タスクを選ぶ前に、全プロジェクトへその日の役割を提案する。
まず週次計画の役割を既定値とし、当日の新しい証拠に応じて具体化または変更する。週次で待機としたプロジェクトを、根拠なく日次で再活性化しない。

| 役割 | 意味 | 原則 |
|---|---|---|
| 集中 | 深い作業を割り当て、主要成果を狙う | 最大2件。主軸は原則1件 |
| 期限対応 | 締切、外部約束、短時間の解除作業を処理する | 必要最小限 |
| 維持 | 小さな前進、確認、次の一手の明確化だけ行う | 時間上限を置く |
| 待機 | 外部待ち、前提未成立、今は動かさない | 原則作業しない |

次の観点を総合し、単純な点数合計では決めない。

1. 長期目標の4本柱への寄与と、今期の戦略的位置づけ
2. 締切、外部コミットメント、他者を止めている依存関係
3. 今の一手で重要な不確実性を解消できるか
4. 投稿直前、検証直前など、完了に近い成果の回収可能性
5. 最近の進展と切替コスト。勢いだけで惰性的に続けない
6. `concern`、overdue、waiting、放置期間。ただしタスク数や古さだけで優先しない
7. 当日の利用可能時間、体調、会議、研究・事務・教育の必要配分

提案には必ず次を含める。

- 集中プロジェクトと、今日それを選ぶ理由
- 期限対応・維持するプロジェクトと時間上限
- 待機するプロジェクトと「今日はやらない」理由
- 優先順位を変える条件
- 全体を見た明示的な「やらないこと」

ユーザーが明示的に決めた優先順位を、客観指標だけで上書きしない。矛盾があれば根拠を示して提案し、決定は確認する。

### 今日の主題

1日の中心となる主題を原則1つにする。必要なら副次的な主題を1つまで置く。

### 今日の問い

その日の作業で答えたい問い、確定したい判断、解消したい不確実性を書く。作業手順を問いにしない。

### 期待する成果

最大3–5件に絞り、各成果に実施主体と完了条件を付ける。
週次の期待成果から、その日に回収できる最小の到達点を選ぶ。週次にない成果を追加する場合は、追加理由を明示する。

**見積が2時間を超える`[本人]`成果は、着手できる単位へ分割してから置く。** 塊の大きさそのものが着手を止める（分割できない性質のものは、理由を書いて塊のまま置く）。

- `[本人]`：思考、意思決定、対話、執筆、会議など本人が担う。
- `[委任]`：エージェントへ任せる調査、実装、検証、整理。
- 共同作業は本人が確定する判断と、委任する処理を分ける。

### エフォート予算

本人が行う作業の見積時間を、次の3区分へ集計する。利用可能時間は配置の上限であり、埋める目標ではない。

| 区分 | 内容 |
|---|---|
| 研究 | 研究、研究のための学習、論文、研究プロジェクト |
| 事務 | 大学事務、調達、業務管理、朝の計画、維持・整備（ツール・規約・リポジトリ） |
| 教育 | 授業、学生対応、採点、教材作成 |

- カレンダー、勤務時間、昼休みを考慮して時間と割合を提案する。
- 週次のエフォート予算と、それまでの実績が分かる場合は残り配分を判断材料にする。
- エージェントの処理時間は予算へ含めない。
- **週次で切った「維持・整備」の枠を超える改善作業は、その日に着手せず `docs/ideas.md` かタスクへ積む。** 価値があっても計画外に入れた分だけ研究時間が削れる。
- 表は研究・事務・教育の3行と、その作業時間の合計を示す`配分計`にする。利用可能時間との差は表の外に`余裕 H:MM`と明記し、配分計と余裕の和を利用可能時間へ一致させる。余裕を埋めるために作業や見積時間を増やしたり、研究・事務・教育へ便宜的に割り振ったりしない。余裕を残したことだけを理由に確認を求めない。

### 制約・予定

会議、締切、昼休み、体調、移動、勤務終了時刻、依存関係を記載する。必要なら停止条件も書く。

## 期限切れタスクのトリアージ

- 今日モード：前日以前の期限切れだけを対象にする。
- tomorrowモード：本日期日のタスクも対象にする。
- 各タスクについて`完了(c) / 延ばす(YYYY-MM-DD) / 削除(d)`をまとめて確認する。
- 安定したtask IDで候補を提示し、承認された完了・延期・削除は`academic_ops.py task complete` / `task edit --set due=YYYY-MM-DD` / `task delete`で処理する。タスク行を直接操作しない。対象が現在の`next_task_id`なら、代替の次タスクまたは状態変更も同じ承認単位で確認し、`close-project-session`など正本を一緒に更新できる手順を使う。
- 優先順位は明示依頼がある場合だけ変更する。

## ユーザー確認と保存

1. プロジェクト優先順位案を提示し、集中・期限対応・維持・待機の判断を確認する。
2. 計画案とタスク候補を提示し、「今日の主題・期待成果・エフォート予算」を確認する。
3. 選んだタスクへ対象日のdueを付けるか確認する。
4. 承認後、`daily/YYYY-MM-DD.md`へ`## 朝の計画`を作成または置換する。他のセクションは保持する。
5. ファイルがなければfrontmatterと`## 朝の計画`を作る。
6. 同日に再実行した場合は重複追記せず、既存の朝の計画を更新する。
7. Markdown本文でリストをネストする場合は、Obsidianの設定に合わせて子項目を半角4スペースでインデントする。YAML frontmatterは通常のYAMLインデントを使う。

## チャット出力

収集した情報と計画案を、当日の判断に役立つ形で簡潔に伝える。保存形式は上記を使う。

長期目標とのつながりの確認は、ときどきでよい。同日の修正では、変更後の流れが分かるよう周辺情報も添える。

内部のファイル参照と行番号はタスク操作に必要な間だけ保持する。同期・audit・文書参照の指摘は、計画判断に関係するものを簡潔に添える。

## 日中の作業報告

朝の計画を保存した後も、同じチャットで短い作業報告を受け取れる。

- 本人の作業、明示された時刻・所要時間、判断、所感、進展、持越しを夕方の日報の証拠として保持する。
- 作業報告を受けた現在時刻をAsia/Tokyoで確認する。受信時刻と本人が述べた活動時刻を区別し、受信時刻だけから活動時間を作らない。
- 返答は短い受領にとどめ、分析や操作は依頼された範囲で行う。通常の報告に保存確認や追加の転記を求めない。
- 日中メモへの永続化は本人が求めた場合に行う。保存済みの朝の計画や他の節を保持する。
- 時間の不足は`daily-report`の時間突き合わせでまとめて確認する。本人がgitやGitHubから取得できる事実を繰り返し報告する必要はない。
