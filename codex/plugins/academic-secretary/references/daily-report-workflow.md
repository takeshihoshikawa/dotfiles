# Daily Report

Read [the shared contract](secretary-contract.md) before acting. This file is the shared workflow for Claude Code, ChatGPT Work, and Codex. Follow the active global instructions when an older example conflicts with them.

`morning`の Introduction に対する Results / Discussion を作る。本人の時間とエージェントの成果を混同しない。
標準化された日報の各節は、`weekly-review`が計画対実績、プロジェクト配分、本人エフォート、委任成果を週単位で集約するための入力にもなる。計画対実績とプロジェクト配分は、重複を避けるため`## 計画と結果`の1表で表す。

## 対象日

- 日付指定があればその日、なければ今日。タイムゾーンは`Asia/Tokyo`。
- 対象日は00:00〜翌日00:00未満。夜間・土日の本人の仕事も含む。夕方はそこまでの振り返りを保存する区切りであり、記録対象の締切ではない。

## 夕方の区切りと翌朝の追記

- 夕方は従来どおり下書きを確認して保存し、そこで振り返りを終える。夜に日報を書く義務や追加の通知は作らない。
- 保存時はfrontmatterの`history_checked_at`に、その収集で得た`scan_started_at`をJSTのISO日時で残す。これは履歴を確認した時点であり、本人の終業時刻ではない。既存値より後へ進め、未確認の材料が残る間は値を進めず、次回も照合対象に残す。
- morningの開始時に、直近の実績入り日報の日付から前日までを日付ごとに調べる。金曜から月曜なら金・土・日が対象。朝の計画だけのノートは「実績入り」に数えない。チェック時点がない旧日報は、その日全体を既存本文と照合する。
- 各日で`session_digest.py --date YYYY-MM-DD --format json`を使い、`history_checked_at`より後の発言・完了・判断を読む。翌日になってから前日の作業を報告した場合もあるため、当朝の会話も照合する。要約に省略があれば元ファイルの該当発言だけを読む。
- 新しい仕事は**実施日**の日報へ追記する。夜の発言が昼の授業を報告していれば昼の項目を更新し、夜の稼働を作らない。日付が特定できなければ確認する。夜間・休日の仕事がない日や、エージェントだけが動いた日には本人の稼働を作らない。
- 既存の成果・時刻・所感と重複させず、明示された事実だけの差分を保存する。この差分保存は本運用への承認に含まれるため毎回は聞き直さない。新たな時間の推定や重大な矛盾だけを朝の確認へまとめ、確認できた部分から反映する。no-save時は書かない。
- 本人の時間が増減したら、その日のエフォート表を全活動の和集合から再計算する。朝の予算・本人の所感・他の節は保持する。古い合計へ追加時間を足すだけにしない。
- 修正した日を含む週報に振り返りが既にあれば、全日報からその週の実績合計・差を再計算し、追加の事実を反映する。本人の「今週のひと言」「生活軸」は変えず、次週計画も自動で変更しない。金曜夜の仕事は前の週報へ入り、次週へ重複計上しない。週の所属はweekly-review手順と既存`period`を使う。
- 夕方の日報作成は通常の下書き確認を行う。翌朝の追記で休日のノートを新しく作る場合も、明示された事実だけなら上記の継続承認で保存できる。未確定事項だけを一度に確認し、朝の計画がなければ予定値は作らない。

## 共通原則

### 本人は時間ベース

- 本人が実際に活動した、根拠のある区間だけを時刻付きで記録する。
- 明示時刻、カレンダー上の参加予定、会話や操作記録から妥当に分かる時刻を使う。
- gitコミット時刻やエージェントの実行時間から本人の労働時間を推定しない。コミットが証明するのはリポジトリ・時刻・件名だけで、作業区間の全体や未記録の詳細は証明しない。
- 並行区間は和集合で集計し、二重計上しない。
- 根拠のない作業を作って稼働時間を増やさない。空白区間の扱いは「時間の突き合わせ」に従う。

### エージェントは成果ベース

- 調査、実装、検証、文書化などを成果単位でまとめる。プロジェクト名は成果の文中で示す。
- 実行開始・終了時刻、夜間の経過時間、並列数は日報本文へ原則記載しない。
- コミットとGitHub Issueは成果の証拠、順序、到達点の把握に使う。
- 本人が採用していない試行や未検証結果は「試行」「未検証」と明記する。
- エージェントの処理時間を本人の稼働時間やエフォートへ含めない。

### Markdown形式

- Markdown本文でリストをネストする場合は、Obsidianの設定に合わせて子項目を半角4スペースでインデントする。
- YAML frontmatterは通常のYAMLインデントを使う。

### エフォート区分

本人の活動だけを分類する。

| 区分 | 内容 |
|---|---|
| 研究 | 研究、研究のための学習、論文、研究プロジェクト |
| 事務 | 大学事務、調達、業務管理、朝の計画、維持・整備（ツール・規約・リポジトリ） |
| 教育 | 授業、学生対応、採点、教材作成 |

## ワークフロー

次の順で進める。

1. 収集
2. 再構成してユーザー確認
3. 保存
4. 完了タスクの確認と処理
5. リポジトリの片づけ

### 1. 収集

可能なものは並列実行する。

- 対象日の`daily/YYYY-MM-DD.md`全文。特に`## 朝の計画`と`## 日中メモ`。
- Google Calendarの対象日の時刻付き予定。終日イベントは除外する。
- 対象日にcloseされた本人作成のGitHub Issues。
- `~/work/projects/`直下の全gitリポジトリと`~/dotfiles`の対象日コミット。
- 現在の会話と、委任時に渡されたセッション引継ぎにある本人の明示時刻、体調、判断、指示、成果。朝の計画が会話で修正されていれば最新の明示的な確定内容を使い、保存済み計画との差を保持する。
- 対象日のセッション履歴の要約（Claude・ChatGPT Work・Codex）。下の`session_digest.py`で取得する。この要約以外の他チャットや別エージェントの履歴が自動的に見えるとは仮定しない。

`~/work/projects/admin/scripts/repo_snapshot.py --fetch --pull-safe --date {対象日} --format json`を実行する。cleanかつbehindのみのリポジトリは自動でpull --rebaseされ、対象日のコミットも同時に取得できる。取得失敗は報告して続行する。

`~/work/projects/admin/scripts/session_digest.py --date {対象日} --format json`を実行する（読み取り専用）。対象日の00:00〜翌日00:00未満の発言を、起動元にかかわらず時刻順に返す。`turns`は発言時刻と先頭160字で、40件を超える場合は先頭20件・末尾20件を残し、`turns_omitted`へ省略数が出る。省略がある場合は`file`の該当部分を読む。`scan_started_at`は収集開始時点。

- `after_hours`は勤務時間外だけに発言があったという参考属性で、除外には使わない。勤務時間をまたぐ会話も夜の発言まで読む。短い完了報告も収集される。
- 自動の承認記録は`omitted`へ出る。雑談かどうかは内容で判断し、短さだけで仕事の報告を捨てない。警告があれば報告し、履歴なしで続行する。
- 日報を作っている自セッションも含まれる。会話で既に見ている内容なので、下書きとの突き合わせで重複として落とす。
- `active_min`は委任・並行を含むので、本人の時間やエフォートの根拠に使わない。`commits`は参考で、0でも作業がなかったことを意味しない。

### 2. 再構成

#### 本人の活動

- 根拠のある活動を時刻順に並べる。
- 会議・授業・受講はカレンダーで補完する。
- **授業・講習の行には、その回の記録を子項目として付ける**（進行・学生の反応・うまくいったこと・来年直すこと。通常授業は`到達 p.X / 予定 p.Y → 遅れ 累計Nコマ`の1行を必ず入れる）。会話にも日中メモにも記録が無い授業は、空白の質問と同じ1回でまとめて聞く。書き先は日報だけで、セッションノート（`courses/*/sessions/`）には書かない（`course-review`が`rg "{科目名}" ~/vault/daily/`で拾う）。
- 昼休み、早退、体調不良、移動など実績解釈に必要な制約を残す。

#### セッション履歴の取り込み

**質問より先に`turns`を読む。** 期待成果の達成（印刷した、送った、通した）、判断、所感は、最初と最後でなく途中の本人の発言に出る。`計画と結果`の判定、完了、所要時間の言及は、まず`turns`を時刻順に読み、答えが出ていれば質問しない。`turns`の160字で足りない時は、該当セッションのファイル（`file`）を開いて本人の発言を読む。質問するのは、`turns`にも会話にも日中メモにも無いことだけで、1回にまとめる（2026-10-14: 履歴にある報告を聞き直して本人に指摘された）。

`session_digest.py`の各件を、朝の計画・現在の会話・日中メモ・カレンダー・gitから作った内容と突き合わせる。

1. 既に下書きの材料に出ている内容（同じ判断、同じ成果）は重ねず、落とす。
2. 出ていない内容は、`やったこと`の該当する区間か、`委任した成果`（最大3件の枠内）か、`気づき`の候補として、**下書きの本文に先に入れる**。質問として並べない。末尾に`（履歴より・要確認）`を付け、本人が直すか消すだけで済むようにする。
3. 本人の判断・採否・方針（何を決めたか、なぜか）を優先して拾う。委任の成果はコミットから取れるので、履歴は判断の方を補う。
4. 朝の計画やほかの節に書かれた内容と矛盾する場合（例: 「未確認」とあるのに、履歴では採否が決まっている）は、訂正の候補として下書きに示す。
5. 夜間・休日も含め、既出の内容を束ねて簡潔にする。件数上限で完了・判断・訂正を落とさない。
6. 学生は番号で表す。面談や人事に関わる内容は、見出しだけを入れ、詳細は既存の専用ノートへの参照にする。
7. 履歴の本文を日報へ貼らない。要約だけを使う。

時間は履歴から決めない。次の「時間の突き合わせ」の根拠は従来どおりで、履歴の稼働分は使わない。

#### 時間の突き合わせ

次の順で根拠を採る。

1. 本人の明示した時刻または所要時間。
2. 前後の作業報告、動かせない予定、日報を作っている時刻、通常の勤務時間。
3. 周辺の活動からの妥当な推論。

- 通常の勤務時間は8:00–16:45、昼休みは11:30–13:00だが、実績の上限ではない。夜間・休日も明示された本人の作業時間を含める。
- 業務上の出張移動は用務の区分へ、日報・週次レビューは事務へ含める。私用移動・昼食・休憩は除く。移動中の仕事と移動時間は重ねて足さない。
- 次の活動や勤務終了の境界から終了時刻を推定するのが自然な場合は、そう読む。
- 30分未満の未解決の空白は確認せずに吸収または省略する。
- 下書きの前に、30分以上の未解決の空白を**まとめて1回だけ**質問する。前後の項目と、こちらの推定候補を添える。
- 推定候補には、その区間に重なる履歴のセッション（プロジェクトと最初の発言）を添える。
- 本人が答えれば解消できる空白について、最終のエフォート表へ`時間未計測`・`算出不可`を残さない。
- 勤務時間はタイムラインの境界であって稼働の証拠ではない。丸1日にするために根拠のない作業を埋めない。
- 研究・事務・教育の合計を実稼働時間と一致させる。7時間15分を照合目標に使うのは、本人が通常どおりの1日だと確認した場合か、昼休みを除いて1日が証拠で埋まる場合だけとする。
- 質問しても解消できない重要な空白は、正確な合計を捏造せず不確実性を明示して残す。

#### 委任した成果

- コミットを時刻順に転記しない。
- 複数コミットを「研究設計の具体化」「パイプライン改善」「検証完了」など意味のある成果へ束ねる。
- **最大3項目**の簡潔な箇条書きにまとめ、プロジェクト別の小見出しは作らない。本人のタイムラインとは分けて置く。
- 成果、到達状態、重要な訂正や未解決点を書く。
- GitHub closed Issueも同じ成果へ統合し、重複させない。

#### 計画と結果

`## 朝の計画`の期待成果を1件ずつ、実績と照合する。

| 判定 | 意味 |
|---|---|
| 達成 | 完了条件を満たした |
| 一部達成 | 重要部分は進んだが未完 |
| 未着手 | 着手証拠がない |
| 変更 | 意図的に別の成果へ切り替えた |
| 想定以上 | 完了条件を超えて進んだ |

`外部待ち`は判定ではなく、未達理由またはプロジェクト状態として`実行・成果／理由`へ記載する。朝の`### プロジェクト優先順位`と、本人の活動・委任成果も同じ行で照合する。

- 集中対象へ本人の深い作業が配分されたか
- 期限対応・維持が設定した範囲で収まったか
- 待機対象へ意図しない作業が流入しなかったか
- 新しい証拠に基づく意図的な優先順位変更だったか、単なる逸脱だったか
- 複数プロジェクトへの分散で主要成果が弱まっていないか

配分評価は`計画どおり`、`意図的変更`、`意図しない流入`のいずれかとする。エージェント成果はプロジェクト進展として記録するが、本人のエフォートへは加算しない。計画と異なるプロジェクトで大きな成果が出た場合は、`朝の役割`を`計画外`とし、理由と次の優先順位への含意を書く。

計画がない日は予定値を捏造せず、`## 計画と結果`を省略する。

#### エフォート配分

1. 本人の活動区間を研究・事務・教育へ分類する。
2. 重複区間を除き、区分別時間と合計を計算する。
3. 朝の予算があれば予定／実績／差を示す。朝の計画にエフォート予算がない場合は、予定を`未設定`、差を`—`とし、0を捏造しない。
4. エージェント成果、昼休みは含めない。
5. 予定と差は日次セルフチェック専用とし、`weekly-review`は実績だけを合計する。

時間の書き方は次に固定する。`weekly-review`が週をまたいで集計するため、表記が揺れるとパースできない。

- **すべて`H:MM`で書く**（`6:15`）。`6時間15分`のような漢字表記を使わない。差は符号を付けて`+1:35`・`-0:42`、ゼロは`±0`とする。
- **`約`を使わない。** 幅のある推定しかできない区間は、時間を書かずに`未計測`とし、何が分からないかを表の下へ1行で書く。
- **予定を置かなかった区分は`未設定`**と書く。`—`や`0:00`で代用しない。`0:00`は「予算として0と決めた」場合にだけ使う。
- **合計行を必ず入れる。** 区分の合計は実稼働時間と一致させる。

#### Discussion

- `## 気づき`には、本人が明示した所感・発見だけを簡潔に書く。作業の事実だけから教訓を作らない。
- `## 次への引継ぎ`には、未解決事項と具体的な次の一手だけを最大3–5件書く。
- 新しいタスクチェックボックスは日報へ作らない。

下書きをユーザーへ提示し、確認を得てから保存する。

### 3. 保存

- 同日に再実行しても各セクションを重複させない。

### 4. 完了タスク

「実際の成果」から完了と判断できる未完タスクをvault全体でタスクIDベースで検索して候補を提示する。
候補とともに、現在の`next_task_id`を閉じる場合の代替の次タスク、または変更後の状態・フェーズ・懸念を同じ承認単位で提示する。確認後、通常のタスクは`python3 ~/work/projects/admin/scripts/academic_ops.py task complete --id {tsk-id} --apply`を使う。
完了させたいタスクが対象プロジェクトの`next_task_id`と一致する場合は、単独のtask completeではなく`close-project-session`を使う（フェーズ・次タスク・懸念を1トランザクションで更新するため）。新規タスクは追加しない。

### 5. リポジトリの状態報告

対象リポジトリのdirty・ahead・divergedを`repo_snapshot.py`の結果から報告する。commit・pushの判断はこのスキルの範囲外。dirtyなリポジトリがあれば`sync-repos`の実行を促す。結果はチャットへ報告し、日報本文には書かない。
