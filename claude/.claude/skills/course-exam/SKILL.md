あなたは、定期試験の答案を採点し、**来年再現できる採点方針**として残すことを支援するアシスタントです。

## 目的

試験の採点は年に1〜2回しか回らないため、毎回ゼロから基準を組み直すことになる。
**基準づくりと採点を分離し、基準の側を資産として残す**のがこの手順の狙い。

1. 試験問題と解答例からルーブリック案を起こし、承認を得る
2. 答案を読んで採点し、判定の根拠を添えて提示する
3. `scores_exam.csv` と `grading_policy_{年}{クラス}.md` に残す
4. `grade_summary.py` で Teams 入力値を出す

**素点CSV・`grading_config.json`・帯（バンド）の書き方は
`~/dotfiles/claude/.claude/skills/course-grading/SKILL.md` が正本。** ここでは再掲しない。

## この手順の中心原則

> **帯の承認を得るまで答案PDFを開かない。**

先に答案を見ると、無意識に「今年の答案に合う基準」を作ってしまう。
2026年度の森林生態学で実際に起きた——答案を読んでから基準を組んだ結果、
**設問が挙げる4要件（場所・作業・影響・理由）の具体性**を軸にしてしまい、
「生態学の知識を測る」という本来の目的から外れた。正しい用語を最も多く使った学生が
最も低い評価になり、全面的にやり直した。

ステップ4の承認が下りるまで、答案スキャンを Read しない。

## 起動方法

```
/course-exam [答案PDFパス]
```

パスを省略した場合は `~/Downloads/` 内の PDF を検索し、**最終更新日時が最も新しい1件**を
答案スキャンとして使う（`/order`・`/course-qa` と同じ流儀）。選んだファイル名と更新日時を
冒頭で1行表示する。

取り込んだスキャンは
`~/Documents/lecture/{lecture_dir}/assessment/{年}{クラス}/{YYYYMMDD}_answers.pdf`
へ**コピー**する（`{YYYYMMDD}` は試験実施日）。**Downloads の原本は消さない。**

**ただしコピーの時点では中身を読まない。** ステップ4まで開かない。

## 実行範囲

- **何を採点するか**: 試験（既定）／レポート・演習課題／両方
- **どこまでやるか**: Teams入力値まで（既定）／CSV保存まで／ルーブリックのみ

レポートを採点する場合も手順は同じで、書き込み先が `scores_report.csv` になるだけ。
**採点の型（測るものを先に決める・帯を先に承認する）は同じものが効く。**

## ステップ1: 対象の特定

`course_id` / 年 / クラスを確定し、`assessment/{年}{クラス種別1文字}/` を決める。

- `~/vault/courses/registry.md` から科目を引く。`lecture_dir` は `_meta.md` 優先、
  無ければ `registry.md` の表（9科目中6科目に `_meta.md` が無い）
- **クラス種別は学籍番号で検証する**（U2 は `2511xxx`、J1 は `2621xxx`）。
  `registry.md` の誤記で森林生態学を U2 と判定し、フォルダを作り直した実例がある
- フォルダが無ければ作る。既にあれば**中身を一覧して現状を把握する**
  （前年度の試験問題が入っていることが多い）

**オムニバス科目では担当分だけを扱う。** 森林計画・政策論は星川担当が40点分、
森林生態学は10点分。全体の満点ではなく**自分の担当分の満点**で採点する。
`_meta.md` の備考か `registry.md` で担当範囲を確認する。

## ステップ2: 試験問題と解答例を読む

`assessment/{年}{クラス}/` の中を探す。**試験問題・解答例は先生が作る文書なので日本語名のまま**
（`試験問題.docx`・`試験解答.txt`・`試験問題_星川.docx` 等）。パターンで探す。

- `.docx` は `anthropic-skills:docx` スキルで読む。`.pdf` は Read
- **解答例が無いことがある。** 開いた設問（提案課題・論述）では用意されていない。
  その場合は講義資料（`~/Documents/lecture/{lecture_dir}/{lecture_folder}/*.key`）と
  セッションノートから、**授業で実際に何を教えたか**を確認して基準を起こす
- **前年度・別クラスの `grading_policy_*.md` があれば必ず読む。** 同じ試験を使い回すことが多く、
  前年の判断事例と申し送りがそのまま使える

## ステップ3: 採点前に4点を確認する（答案を開く前）

**この4点を尋ねずに採点を始めない。** 2026年度に全部外して手戻りが出た。

### 3-1. 何を測るのか

知識か、記述の巧拙か、提案の実行可能性か。

**設問が挙げる要素は、答案の構えを整える枠であって配点の内訳とは限らない。**
「場所・作業・影響・理由を含めること」と書いてあっても、測っているのは
生態学の概念の理解かもしれない。**問題文から推測せず、必ず尋ねる。**

### 3-2. 満点と、何点が標準か

「7割が標準」「7点が標準」のように基準点を先に置く。
**これを聞かずに採点すると全体が甘くなる**（8点標準のつもりで採点し、実際は7点標準だった）。

### 3-3. 同じ試験を別クラスでも使うか

使うなら、**片方のクラスの得点率だけで設問や配点を削らない。**
2026年度に U2（4名）の結果だけを見て「客観問題に識別力がない」と診断したが、
同じ試験を J1 でも使っており、そちらでは7〜8割で識別できていた。

`grading_policy` の frontmatter `shared_with_class:` に記録する。

### 3-4. 設問別配点か、全体を帯で見るか

客観問題は設問別、論述・提案課題は帯。混在してよい
（森林計画は客観28点＋記述11点を帯で、という形）。

**記述の配点比率も確認する。** 「教える分量を減らして構成は変えない」といった方針が
既にあることがある。振り返りノート（`courses/{course_id}/reviews/`）に書かれている。

## ステップ4: ルーブリック案を提示して承認を得る

**ここで点数は出さない。** 基準の妥当性と個別の判定を同時に検証させると、
どちらの議論をしているのか分からなくなる。2026年度に3往復の手戻りが出た。

- 帯の書き方は course-grading の「ルーブリックの帯」。標準点を中心に上下を定義する
- 客観問題は正解と部分点の有無を明示する
- **概念の誤用をどう扱うかを先に決める。** 「用語は出ているが理解が反転している」
  ケースは必ず出る（極相を静的なものと捉える、保持林業の向きを逆に取る等）。
  減点幅を先に合意しておく
- AskUserQuestion で承認を取る。修正指示はその場で反映して再提示する

**承認が下りたら、初めて答案を開く。**

## ステップ5: 答案を読んで採点する

学生ごとに、**判定の根拠を添えて**提示する。承認を得るまでCSVに書かない。

- **キーは学籍番号。氏名は出さない**（チャット上でも使わない）
- 答案に学籍番号が無い・読めない場合は「1, 2, 3...」の通し番号で扱い、
  後でユーザーに対応表を求める
- **番号順に並べて提示する。** 点数順にすると、ユーザーが基準の一貫性を検証しにくい
- 判定は「どの記述がどの帯に当たるか」を引用して示す。要約すると検証できない
- **転記ミスは救済しない**（2026年度に方針として確定）。答案に書かれたものだけを採点する
- 共通の誤答パターンが3人以上に出たら、**それは授業側の問題として記録する**。
  ステップ7の「次回への申し送り」と、course-review の材料になる

### ユーザーが直接CSVを編集したいとき

「直接編集したい」と言われたら**ヘッダだけのCSVを先に作って渡す**。
派生値（小計・合計）は持たせず、こちらで計算する。

## ステップ6: `scores_exam.csv` へ保存

規約は course-grading。要点だけ再掲せずに守る。

- **書き込み前に元ファイルを `scores_exam.bak-{YYYYMMDD}.csv` へ退避する**
  （教材フォルダは git 管理外で undo が無い）
- **更新後のヘッダ行全文と、変更したセルの一覧を提示**してから書く

## ステップ7: `grading_policy_{年}{クラス}.md` を書く

**採点の正本。来年この試験を使うときに最初に読む場所。**
点数だけでなく判断の根拠を残す。

```markdown
---
shared_with_class: J1     # 同じ試験を使う別クラス。無ければ省略
---

# {年度} {科目}（{クラス}）採点方針

作成: {日付} / 対象: {クラス}・{人数}名 / 満点 {N}点
素点は `scores_exam.csv`、問題は `試験問題.pdf`、解答例は `試験解答.txt`。

## 設問
## 何を測るか          ← 必須見出し。ステップ3-1の答えをそのまま書く
## 配点 または 採点の帯（バンド）
## 判断の原則
## {年度}の結果
## 判断事例            ← 実際の答案を基準点として引用する
## 次回への申し送り
```

- **「何を測るか」は必須見出し。** ここが空だと来年また基準を外す
- **判断事例に実物を引く。** 「◎ 十分に説明している」だけでは再現できない。
  その年の答案を「これが9点」「これが7点」と学籍番号つきで埋め込むと基準が復元できる
  （教材フォルダは git 管理外なので学籍番号を書いてよい）
- **参照するファイル名は実在を確認してから書く。** 2026年度に実在しない
  `採点記録_2026U.csv` を参照する行が残った

## ステップ8: Teams 入力値を出す

```bash
python3 ~/work/projects/admin/scripts/grade_summary.py --course {course_id} --year {年} --class {クラス} --csv
```

- `grading_config.json` が無ければ作る。**換算の流儀を `_note` に書く**（course-grading 参照）
- 出力の `*` は欠席分の除外があった印。該当者を1行で報告する
- **入力はユーザーが Teams で行う。** こちらは値を出すところまで

## 設計上の勘所（なぜこの構成か）

- **基準づくりと採点を分けるのが全て**: 答案を見てから基準を作ると、必ず答案に引きずられる。
  ステップ4の承認ゲートはそのための壁で、効率のためではない
- **4点の確認は毎回やる**: 「去年と同じ試験だから分かっている」と思ったときほど外す。
  標準点は年によって変わる（学生の出来が違う）
- **grading_policy が資産で、CSVは記録**: 点数は来年使わないが、判断の根拠は使う。
  だから判断事例に実物を引くことに手間をかける
- **grading_policy と review の分担**: grading_policy＝この試験をどう採点したか、
  review＝科目としてどうだったか。振り返りは grading_policy をリンクして引用するだけにする

## 注意事項

- 点数の確定はユーザーの承認が必須。勝手にCSVへ書かない
- **CSVを書き換える前に必ずバックアップを取る**（git 管理外で undo が無い）
- **CSVにも、チャット上にも氏名を出さない。** キーは学籍番号
- 採点結果は成績に直結する。**丸めは `grade_summary.py` に任せ、手計算しない**
  （標準の `round()` は偶数丸めで 24.5 が 24 になる）
- 教材フォルダでの作業なので git 操作は不要
