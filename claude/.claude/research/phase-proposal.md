# フェーズ: 申請書

公募研究計画書（科研費・学術変革・受託等）を書き、提出物を作るときの手順。
`proposals/` の位置づけとディレクトリ構造は `~/dotfiles/claude/.claude/research-project-conventions.md` が正本。

## 提出物のワークフロー

```
proposals/{YYYY}-{種別}/drafts/*.md
        ↓ pandoc --reference-doc=様式/template.docx
proposals/{YYYY}-{種別}/output/研究計画調書.docx     ← 毎回上書き（gitignore）
        ↓ コピー（提出したときだけ）
proposals/{YYYY}-{種別}/submitted/{YYYYMMDD}_{種別}_{略称}.docx   ← git 追跡・以後変更しない
```

**markdown が真のソース。** Word は最終出力としてのみ生成する。共同研究者と Word で授受する
場合も、md → docx 変換を都度回す（Word 側で直接編集した内容を md へ戻す運用にしない）。

**提出物もリポジトリで完結させる**（2026-07-29 変更。以前は `~/Documents/grant/` へ iCloud
アーカイブしていた）。`output/` はビルドのたびに変わるので、提出した事実を残すには別ディレクトリが要る。
git に残るのは `drafts/` の md、`figures/`・`refs/`・`budget/`、そして `submitted/`。

## AI の使い分け

研究計画書では「自然で読みやすい文章」よりも**研究の芯が伝わること**を優先する。
単一 AI に通しで書かせるより、**工程を分けて視点を分散させる**ほうが有効。

分散させる理由は、どの製品が優れているかではなく、**同じモデルに芯の固定と可読性の向上を
同時にやらせると、必ず可読性が勝って芯が削られる**から。工程を分ければ、削られたことに
次の工程で気づける。

### 3 フェーズを回す

| | 目的 | 見るもの |
|---|---|---|
| **Phase A: 芯を固定する** | 本当に新しいものは何か / 絶対に失ってはいけない概念は何か / 差別化軸は何か | 読みやすさ・文章美・キャッチーさは**見ない**。AI の自然化圧力に負けない |
| **Phase B: 査読者可読性を上げる** | 一読で理解できるか / 何が新しいか即座に伝わるか / 読み疲れしないか | 圧縮・見出し改善・タイトル調整・語感調整 |
| **Phase C: 論理を再検証する** | 抽象化で本質が消えていないか / 差別化が弱まっていないか / 用語がブレていないか / 方法と目的が対応しているか / タイトルと本文が一致しているか | Phase B が削ったもの |

必要に応じて A → B → C を繰り返す。**A と B は別の担い手に割り当てる**（同一モデルで
やる場合もセッションを分け、B の出力を A の基準で検証する工程を必ず挟む）。

どのモデルをどのフェーズに割り当てるかは `~/dotfiles/claude/.claude/research/ai-role-assignment.md`
（**観測であって規範ではない**。モデル世代が変われば変わる）。

### 特に注意すること

- **「読みやすい」は「強い研究」ではない。** 大型科研では、少しクセがあっても・密度が高くても
  研究の芯を保持したほうが強い場合がある
- **AI に新規性を定義させすぎない。** AI は既存カテゴリへ回帰させる傾向が強い。特に学際研究では
  「既存分野の境界にある違和感」こそが新規性であることが多く、これは人間が保持する必要がある
- **人間の役割は、本当に重要な問いを保持すること。** ここは工程の分割では代替できない
- 文書 QA（用語統一 / 図表整合 / budget–method consistency / セクション間の矛盾検出 /
  「本文中で支えられていない主張」の検出）は AI 側に寄せてよい。人が読み通すより網羅的になる

## 文献

引用文献はプロジェクト別の papis ライブラリで管理する。**ライブラリはリポジトリの外**
（iCloud `~/Documents/papis/{project}/`）。知識ベース `kb` から必要なものをコピーして使う一方向フロー。

リポジトリに入るのは生成した `proposals/{YYYY}-{種別}/refs/refs.bib` だけで、直接編集しない。
規約は `~/dotfiles/claude/.claude/papis-conventions.md` が正本。**文献を触るときは読む。**

## 提出後

提出版を `proposals/{YYYY}-{種別}/submitted/{YYYYMMDD}_{種別}_{略称}.docx` にコピーしてコミットし、
**push する**。提出版の正本はこのリポジトリだけなので、push しないとバックアップが存在しない。

採択結果を待つあいだ並行作業が無いなら、vault のプロジェクトノートの `status` を `waiting` にする。
