# 記録管理ポリシー

研究・管理の記録をどこに置き、どう腐らせないかの規約。データそのものの置き場は
`data-management-policy.md`（raw / interim / processed / outputs）が正本で、こちらは**記録**を扱う。

根拠と実測は `~/work/projects/admin/reports/task-management-split-2026-08-13.md` と
`~/work/projects/admin/reports/research-docs-survey-2026-10-31.md`。

## 3つの原則

個別のルールに迷ったら、この3つから判断する。

1. **正本は1つ。** 二重に置かない。複製が要るなら**要約1行＋ポインタ**に留める
2. **溜まる器を作らない。** 実行を待つ項目を溜める器と、日付順の作業ログは作らない
3. **結果が出たら台帳を更新する。** 陳腐化は時間ではなく**結果**によって起きる

---

## 原則1: 正本は1つ

### 置き場

**この表に無い器は作らない。** 「置くもの」の列から引けば、書こうとしているものの置き場が決まる。

| 器 | 置くもの | 置かないもの |
|---|---|---|
| Obsidian `tasks.md` | 期限があるか他人が絡む作業。分野は問わない | 期限の無い検討事項。リポで完結する判断の記録 |
| Obsidian `meetings/YYYY-MM-DD_タイトル.md` | 会議の文脈・決定事項・その場で決まったアクション | ステータス管理 |
| vault `projects/{name}.md` | プロジェクト間で効く文脈（概要・仮説・関係者・意思決定） | チェックボックス。状態（フェーズ・次の一手・懸念） |
| リポ直下の `project-status.yaml` | プロジェクトの状態8フィールド | それ以外すべて |
| リポ `CLAUDE.md` | 概要・ディレクトリ構成・実行方法・規約からの逸脱・文書へのポインタ・**やって欲しくないこと**・常に効く現場の事実 | **作業ログ・未着手の検討事項・所見や撤回の記録・懸念の逐次追記・主張の文** |
| リポ `docs/decision-log.md` | 本人の判断とその理由・却下と保留・誤った判断の経緯・古い項目への訂正の注 | 作業の記録。主張の今の状態。数値の写し |
| リポ `docs/{論点}.md` | 1つの論点の解析・根拠・撤回 | 複数論点の混在。日付順の束ね |
| リポ `CLAIM-MAP.md` | 何が言えて何が言えないか（原則3） | 経緯。数値の正本 |
| リポ `docs/data-provenance.md` | データの出所・照会の仕様 | |
| リポ `outputs/reports/YYYY-MM-DD_{論点}.md` | 特定の調査・実験の結果 | 継続的に参照される規範（`docs/` へ） |
| git のコミットメッセージ | 何を変えたか（作業記録）と短い理由 | 本人の判断の経緯 |
| `scripts/experiments/` | コードの試行錯誤（`research/phase-analysis.md`） | |

- 外部との約束・返信待ちは、発生した場所（`tasks.md` か `meetings/`）に置き、**転記しない**。
- `CLAUDE.md` の生成ブロックと vault `projects/*.md` の frontmatter は `project-status.yaml` からの**生成物**で、手で書かない。

### decision-log

- **日付順に1ファイルへ追記する。** 経緯は Claude に聞いて引くので、日付を知らなくても引ける。
- **本人の判断は「本人」と書いて示す。** 「ユーザー」「著者」と混ぜない。
- 古い項目が実際と違うと分かったら、消さずに訂正の注を付ける。
- `CLAUDE.md` からはポインタ1行だけで参照する。

### 論点ファイル

- **1論点1ファイル。** 日付順に1ファイルへ積み上げない（日付を知らないと引けなくなる）。
- 撤回・却下は消さない（原則3）。`CLAUDE.md` からはポインタ1行だけで参照する。
- `docs/` と `outputs/reports/` の使い分けは決めない。**迷ったら既存の似た文書と同じ場所に置く。**

### 教訓

**`docs/lessons.md` は新しく作らない。** 既にあるリポは引き続き使ってよい。
教訓にあたるものは、中身で置き場を分ける。

| 教訓にあたるもの | 置き場 |
|---|---|
| 誤った判断の経緯（なぜ間違えたか） | `docs/decision-log.md` |
| 検査にできる規範 | テスト・スクリプトの検査 |
| 主張の範囲（言ってはいけないこと） | `CLAIM-MAP.md` の forbidden |
| 可能だけどやって欲しくないこと・常に効く現場の事実 | `CLAUDE.md` |

## 原則2: 溜まる器を作らない

### 作らないもの

- **やりたいことリスト**（実行を決めていない項目の在庫）
- **順番待ちの在庫**（「次にやること」を複数並べたもの。`queue.md`）
- **日付順の作業ログ**（`worklog.md`）。作業記録はコミットメッセージが持つ

判断の記録（decision-log）は実行を待つ項目ではなく台帳であり、これに当たらない。

### Obsidian に置く条件

**期限があるか、他人が絡むか。** これだけ。「リポ内で完結するか」で切らない。

**「due 無し」というカテゴリを作らない。** 週次レビューで3択にする——
**due を付ける／リポの文書（論点ファイルか decision-log）へ落とす／捨てる**。

Obsidian に入れると決めた後のセクション振り分けと記法はグローバル `CLAUDE.md` が正本。
ここでは入口の選択だけを決める。

### タスク行に経緯を溜めない

- タスク行が持つのは**次の1手・期限・待ち先**だけ。判断の経緯・却下した選択肢は
  `docs/decision-log.md`、解析の中身は `docs/{論点}.md` へ置き、タスク行からは**パス1本のポインタ**を張る。
- **内容を要約し直さない。** 要約した時点で正本が2つになり、両方が別々に腐る。
- **判定は「次の1手が1つに定まるか」。** 定まらないなら、経緯を出すか、タスクを分ける。
- **境界を跨いで同じ文を書かない。** タスク行は行き先を1つ名指しするだけにし、
  そこにある論点の列挙や件数を書かない（1点決着した時点で片方が嘘になる）。

### 次の一手は在庫ではない

1個・上書き・**翌朝の自分向け**（`/morning` が全リポ横断で読む）。
`next_task_id` と `next_action` の使い分けは、Obsidian に置く条件がそのまま伝播する。

| 次の一手が | 書く場所 |
|---|---|
| 期限があるか他人が絡む（＝Obsidian にタスクがある） | `next_task_id` でそれを指す |
| Claude とリポ内で完結する dev 作業 | `next_action` に自由記述 |

スキーマと検査規則は `~/work/projects/admin/CLAUDE.md`「次の一手の2択」が正本。

## 原則3: 結果が出たら台帳を更新する

### 陳腐化はイベント駆動である

1つの問題が解けると、それに依存していた前提・主張・計画がその瞬間に失効する。
したがって**経過日数では捕まらない**。活発なプロジェクトほど失効が多いのに、最終更新からの経過は短いままになる。

### 主張の台帳を持つ

`CLAIM-MAP.md` 型。**何が言えて何が言えないか**を、主張ごとに ID を振り、対象（sample）・
推定するもの（estimand）・強さ（strength）・言ってよい文言（allowed）・言ってはいけない文言（forbidden）の列で並べる。

- 置き場は、原稿があればその隣（`outputs/papers/{name}/`）、まだ無ければ `docs/`。
- この表が「今どこまで言えるか」の唯一の正本で、`CLAUDE.md`・スライド・原稿はここを参照する。
- **ほかの文書から主張の文を写さない。** 参照は主張の ID・数値の台帳のキー・図表番号に限る
  （写しがあると、撤回のたびに伝播が要り、漏れる）。
- **失効は表の中に記録する**（旧根拠を消して、いつ何によって否定されたかを残す）。撤回した判断の経緯は decision-log に書く。
- 既にある `docs/contribution.md` は使い続けてよい。新しく作るときは CLAIM-MAP 型にする。

### 結果が出たら台帳を更新するまでが1つの作業

トリガーは時間ではなく**結果が出たこと**。作業を終えるとき（`close-project-session`）に確認する。

1. この結果で**どの主張の判定・根拠が変わったか**
2. **失効した前提に依存していた計画・タスクはあるか**
3. 判断が変わった・誤りが見つかったなら、経緯を decision-log に書いたか。検査にできるものはテストにしたか

**台帳の更新はユーザーの承認を経る。** 「更新すべきか」は解析の中身の判断で、機械にも
第三者にも決められない。提案 → 承認 → 書き換え、の順で行う。

### 撤回を消さない

取り消し線と日付つきの印で残す。消すと**同じ主張が再生産される**。
「及ばないと確認した」事実も同じ理由で残す。

### 機械で見られる範囲／見られない範囲

| 見られる | 見られない |
|---|---|
| 参照先・`§`番号・パスの実在（`~/work/projects/admin/scripts/doc_refs.py`） | 主張の**判定**が古いままかどうか |
| 見出しの重複・状態マーカーの重複（＝撤回済みの節が残っている） | 個人名・組織名が公開範囲を越えていないか |
| 台帳ファイルの未更新期間＋その間の解析コミット数 | 「更新すべきだった」かどうか |

**コミット単位で「解析コミットが台帳に触れていない」は検査しない。** 台帳の更新は独立したコミットで
行われ、解析コミットの大半は台帳に影響しないので、偽陽性だらけになる。
検査するなら**台帳ファイル自身の未更新期間**で、判定は warning に留める。

## 公開範囲

**正本の可視性が下流すべてを決める。** `next_task_id` を使うと Obsidian タスクの本文が
`CLAUDE.md` の生成ブロックへレビューを経ずに転記される。Obsidian は非公開前提で書く場所で、
相手先名・担当者名・金額が入っている。

- **公開リポでは `next_task_id` ではなく `next_action`（自由記述）を使う。** 書くときに内容を見られる。
- **例外**: `status: waiting` は `next_action` を持てない。公開リポの waiting は
  `next_task_id` しか選べないので、**タスク本文を公開前提で書く**。
- **関係者・提供元・金額は vault のプロジェクトノート**（「## 関係者」節）。リポ側はポインタだけ持つ。
- 混入に気づいたら現在のファイルから消す。**git 履歴の書き換えはしない**
  （他端末との同期を壊すリスクの方が大きく、公開後は実効性も乏しい）。

## 迷ったときの既定

**迷ったらリポの文書（論点ファイルか decision-log）。**

取り違えのコストが非対称だから——誤ってリポの文書に置いた締切は自分が困るだけだが、
Obsidian に載らなかった外部との約束は**相手との約束を損なう**。
