# 記録管理ポリシー

研究・管理の記録をどこに置き、どう腐らせないかの規約。データそのものの置き場は
`data-management-policy.md`（raw / interim / processed / outputs）が正本で、こちらは**記録**を扱う。

発効 2026-08-25。**2026-09-25 まで移行期間**（末尾「## 移行期間」）。
根拠と実測は `~/work/projects/admin/reports/task-management-split-2026-08-13.md`。

## 3つの原則

個別ルールを覚えていなくても、この3行から判断できる状態にしてある。
2026-08-13〜25 のパイロットでは、**個別ルールは1〜2日で破られ、原則だけが実運用を説明できた**。

1. **正本は1つ。** 二重に置かない。複製が要るなら**要約1行＋ポインタ**に留める
2. **溜まる器を作らない。** 追記され続けて上書きされないものは器にしない
3. **結果が出たら台帳を更新する。** 陳腐化は時間ではなく**結果**によって起きる

## 原則1: 正本は1つ

### 配置マップ

**「いま書こうとしているものは何か」から引く。** 正本の欄が「生成」のものは手で書かない。

| 書こうとしているもの | 置き場 | 正本 |
|---|---|---|
| 期限のある作業（プロジェクト） | Obsidian `tasks.md` `## projects` または `meetings/` | 正本 |
| 期限のある作業（大学事務・授業・分類に迷うもの） | Obsidian `tasks.md` の `## admin` / `## teaching` / `## inbox` | 正本 |
| 外部との約束・返信待ち | 発生した場所（`tasks.md` か `meetings/`）。**転記しない** | 正本 |
| 会議の文脈・決定事項 | Obsidian `meetings/YYYY-MM-DD_タイトル.md` | 正本 |
| プロジェクトの状態（フェーズ・次の一手・懸念・更新） | リポジトリ直下の `project-status.yaml` | 正本 |
| 同上の表示 | `CLAUDE.md` の生成ブロック／vault `projects/*.md` の frontmatter | **生成** |
| **判断の根拠・却下と保留の理由** | リポの `docs/{論点}.md` | 正本 |
| 調査・実験の結果 | リポの `outputs/reports/YYYY-MM-DD_{論点}.md` | 正本 |
| 恒久的な教訓 | リポの `docs/lessons.md` | 正本 |
| 何が言えて何が言えないか | リポの `docs/contribution.md`（→ 原則3） | 正本 |
| データの出所・照会の仕様 | リポの `docs/data-provenance.md` | 正本 |
| 何を変えたか | git log | 正本 |
| コードの試行錯誤 | `scripts/experiments/`（`research/phase-analysis.md`） | 正本 |
| プロジェクト間で効く文脈（概要・仮説・関係者・意思決定） | vault `projects/{name}.md` 本文 | 正本 |

**この表に無いものは作らない。** やりたいことリスト・順番待ちの在庫・日付順の作業ログは
置き場を持たない（原則2）。

### 器ごとの受け入れ範囲

表を引かずに判断するための、器の側からの定義。

| 器 | 受け入れる | 受け入れない |
|---|---|---|
| Obsidian `tasks.md` | 期限があるか他人が絡む作業。分野は問わない | 期限の無い検討事項。リポで完結する判断の記録 |
| Obsidian `meetings/` | 会議の文脈・決定事項・その場で決まったアクション | ステータス管理 |
| vault `projects/*.md` | プロジェクト間で効く文脈 | チェックボックス。状態（フェーズ・次の一手・懸念） |
| `project-status.yaml` | 状態8フィールドのみ | それ以外すべて |
| リポ `CLAUDE.md` | 概要・ディレクトリ構成・実行方法・規約からの逸脱・生成ブロック・論点ファイルへのポインタ | **作業ログ／未着手の検討事項／所見・撤回の記録／懸念の逐次追記** |
| リポ `docs/{論点}.md` | 1つの論点についての判断・根拠・撤回 | 複数論点の混在。**日付順の束ね** |
| `outputs/reports/` | 特定の調査・実験の結果報告 | 継続的に参照される規範（`docs/` 側へ） |
| git log | 何を変えたか | なぜその判断に至ったか（論点ファイルへ） |

`CLAUDE.md` の「受け入れない」が肥大防止の実効部分である。`phase-setup.md` の「最低構成」は
**書くもの**の規定で、書かないものはどこにも無かった。それが 76KB 化を許した穴だった。

### 論点ファイルは日付順に束ねない

1論点1ファイル。**日付順に1ファイルへ積み上げない**——326KB・`#` 見出し1個・入口が43個の
日付ポインタ、という状態になり、日付を知らないと引けなくなる（実例）。
撤回・却下は消さない（原則3）。`CLAUDE.md` からはポインタ1行だけで参照する。

**`docs/` と `outputs/reports/` の使い分けは規約で決めない。** 実測すると日付付きの報告書も
継続更新されており、「継続更新 対 時点の記録」という切り分けは実態に合わない。
**迷ったら既存の似た文書と同じ場所に置く。**

## 原則2: 溜まる器を作らない

### 作らないもの

- **やりたいことリスト**（実行を決めていない項目の在庫）
- **順番待ちの在庫**（「次にやること」を複数並べたもの）
- **日付順の作業ログ**

パイロットの実測: やりたいこと在庫は8項目中1件しか実行されず（12.5%）、初週で25KBまで育って
6日で沈黙した。順番待ちは12項目あって**登録が実行を決めた例がゼロ**（登録日＝着手日）。
一方、**1個だけの可変ポインタ**（次の一手）は12日で41回書き換わり、
**期限つきタスク**は期限超過0件で回っていた。**溜まる器だけが腐る。**

### Obsidian に置く条件

**期限があるか、他人が絡むか。** これだけ。
「repo内で完結するか」で切らない——パイロットで遵守率0/3（ルールを書いた1〜2日後に作成者自身が破った）。

**「due 無し」というカテゴリを作らない。** 週次レビューで3択にする——
**due を付ける／論点ファイルへ落とす／捨てる**。
陳腐化は正確に「期限も他人も無いタスク」に集中していた（3ヶ月半停滞の実例あり）。

Obsidian に入れると決めた後の**セクション振り分けと記法**はグローバル `CLAUDE.md` が正本。
ここでは入口の選択だけを決める（層が違う）。

### 次の一手は在庫ではない

1個・上書き・**翌朝の自分向け**（`/morning` が全リポ横断で読む）。置き場の2択には関与しない。
`next_task_id` と `next_action` の使い分けは**原則2の2択がそのまま伝播する**。

| 次の一手が | 書く場所 |
|---|---|
| 期限があるか他人が絡む（＝Obsidian にタスクがある） | `next_task_id` でそれを指す |
| Claude とrepo内で完結する dev 作業 | `next_action` に自由記述 |

スキーマと検査規則は `~/work/projects/admin/CLAUDE.md`「次の一手の2択」が正本。

## 原則3: 結果が出たら台帳を更新する

### 陳腐化はイベント駆動である

**1つの問題が解けると、それに依存していた前提・主張・計画がその瞬間に失効する。**
研究では結果が出るたびに必ず何かが無効になる。したがって**経過日数では捕まらない**——
活発なプロジェクトほど単位時間あたりの失効が多いのに、`stale_days`（最終更新からの経過）は
ゼロ近傍のままになる。

### 主張の台帳を持つ

`docs/contribution.md` 型。**何が言えて何が言えないか**を、根拠と限定つきで採番して並べる。
この表が「今どこまで言えるか」の唯一の正本で、`CLAUDE.md`・スライド・原稿はここを参照する。
**失効は表の中に記録する**（旧根拠を消して、いつ何によって否定されたかを残す）。

### 結果が出たら台帳を更新するまでが1つの作業

トリガーは時間ではなく**結果が出たこと**。作業を終えるとき（`close-project-session`）に確認する。

1. この結果で**どの主張の判定・根拠が変わったか**
2. **失効した前提に依存していた計画・タスクはあるか**
3. 新しい教訓はあるか（`docs/lessons.md`）

**台帳の更新はユーザーの承認を経る。** 「更新すべきか」は解析の中身の判断で、機械にも
第三者にも決められない。提案 → 承認 → 書き換え、の順で行う。

### 撤回を消さない

取り消し線と日付つきの印で残す。消すと**同じ主張が再生産される**
（撤回済みの数値がスライドに残り、後日落とす作業が発生した実例）。
「及ばないと確認した」事実も同じ理由で残す。

### 機械で見られる範囲／見られない範囲

| 見られる | 見られない |
|---|---|
| 参照先・`§`番号・パスの実在（`check_claude_md.py` 型） | 主張の**判定**が古いままかどうか |
| 見出しの重複・状態マーカーの重複（＝撤回済みの節が残っている） | 個人名・組織名が公開範囲を越えていないか |
| 台帳ファイルの未更新期間＋その間の解析コミット数 | 「更新すべきだった」かどうか |

**コミット単位で「解析コミットが台帳に触れていない」は検査できない**——台帳更新は独立コミットで
行われ、解析コミットの大半は台帳に影響しないため、偽陽性だらけになる（実測で155件中153件）。
検査するなら**台帳ファイル自身の未更新期間**で、判定は warning に留める。

## 公開範囲

**正本の可視性が下流すべてを決める。** `next_task_id` を使うと Obsidian タスクの本文が
`CLAUDE.md` の生成ブロックへ**レビューを経ずに**転記される。Obsidian は非公開前提で書く場所なので、
相手先名・担当者名・金額が普通に入っている。

- **公開リポでは `next_task_id` ではなく `next_action`（自由記述）を使う。**
  自由記述は書くときに内容を見るので、手書き時代と同じ安全性に戻る
- **例外**: `status: waiting` は `next_action` を持てない。公開リポの waiting は
  `next_task_id` しか選べないので、**タスク本文を公開前提で書く**
- **関係者・提供元・金額は vault のプロジェクトノート**（「## 関係者」節）。リポ側はポインタだけ持つ
- 混入に気づいたら現在のファイルから消す。**git 履歴の書き換えはしない**
  （他端末との同期を壊すリスクの方が大きく、公開後は実効性も乏しい）

## 迷ったときの既定

**迷ったら論点ファイル。**

理由は取り違えのコストが非対称だから——誤って論点ファイルに置いた締切は自分が困るだけだが、
Obsidian に載らなかった外部との約束は**相手との約束を損なう**。
判断を有限時間で終わらせるための逃げ道で、これが無いと2択が3択になる。

## 移行期間

**2026-08-25 発効・2026-09-25 まで**。既存の状態はこの間そのままでよい。

| 状態 | 移行期間中 | 期限後 |
|---|---|---|
| `project-status.yaml` 未移行 | 許容（`audit` は warning） | 棚卸しの対象 |
| `CLAUDE.md` に待ち行列・作業ログが残る | 許容 | 論点ファイルへ出す |
| Obsidian に due 無しタスクが残る | 許容 | 週次レビューで3択 |
| 主張の台帳（`contribution.md` 型）が無い | 許容 | 必要かをプロジェクトごとに判断 |

**期限は「error に上げる日」ではなく「棚卸しをする日」。**
`status_not_migrated` を error にすると、このマシンに無いリポが常時エラーになる。
移行の督促は `audit` の warning と週次レビューで足りる。
